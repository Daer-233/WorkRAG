## 四、卡片问题的准确根因

Host 当前在收到 Runner 的第一个输出结果时才调用 `create_message_card`。钉钉库创建卡片时设置 `content=''`、`answer=''`、`flowStatus='1'`。非空正文更新会调用 `send_card_message`，把状态变为 2；完成时为 3。

原插件等待检索／模型完成后才输出，所以等待期间没有卡片。0.3.6 加了“正在处理”正文，占位字虽早到，却马上使卡片从原生等待态进入正文态，不是用户要的转圈加载卡片。

0.3.7 起改为先输出空 MessageChunk（content 和 all_content 均为空），仅触发原生卡片创建；答案准备好后发送累计 all_content 快照，最后完成。目标是在推理期间保持 flowStatus=1，且不把占位文字混入最终答案。

必须再让用户在钉钉端确认转圈和边框。接口收到空首帧不等于钉钉客户端的具体样式已经验收。

最新接口实测：空首帧约 0.484 秒到达，最终回答正常完成，结果在 `native-waiting-acceptance.json`。当前累计 55 项工作流／检索回归通过；原 54 项基线基础上增加了“图片／文件选择不默认为图片”的检查。

### P1：图片／文件选择与媒体发送

- 用户先确定资料；有多份引用时不能将“图片”错误关联到任意一份。
- 选择图片：后端再次检查资料版本及白名单，读取签名预览并验证类型、大小、数量，上传为钉钉可访问的媒体，再写入卡片变量。
- 图片区域使用模板原生 CollapsePanel，默认折叠；用户展开后才展示网格。不得用 Markdown 的 HTML details 假装钉钉原生折叠已实现。
- 选择文件：只发送该资料当前版本对应的受控原件／整理稿，使用原生附件发送，并按平台返回结果记录成功、失败或未知；不能用“找到文件名”代替附件成功。
- 图片和文件发送需绑定当前入站会话及用户，限制重试并去重，不允许模型指定任意收件人或本机路径。
- Host 的钉钉适配器在最终 reply_message_chunk 中已有 `bot.send_attachment` 调用；优先研究官方 SDK 输出附件／资源接口与该现有路径。普通文字转换器忽略 File 并不代表整个平台没有附件发送能力。
- 当前 Runner 只输出文本，需补受控媒体获取与输出接线；SDK 的 from_file_base64 存在不代表消息转换已覆盖该类型，必须读实际实现并测通。

### P3：真实单聊完整验收

在用户选定的本人单聊，逐项验证：

1. 原生处理中转圈及样式 → 正文 → 正常结束。
2. 查询设备借用第二步，答案和引用正确。
3. 选择图片，卡片显示折叠区域，默认收起，展开后能在手机／桌面钉钉看到实际图片。
4. 选择文件，实际收到可打开的 DOCX，名称、内容和版本一致。
5. 点赞进候选但不自动发布；点踩留原因；重复回调与改评正常。
6. 多资料歧义、过期引用、越权、发送失败、重试与服务重启不造成错发或重复投递。

每项分别记录代码完成、平台响应、用户目验，不能用“路由 delivered”代表文件／图片／卡片都成功。
